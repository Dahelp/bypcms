# Приёмка обновлений и восстановления — 7 ноября 2026

## Реализованный путь

Публикация подготовленного выпуска владельцем → подписанный каталог → проверка
лицензии и совместимости → скачивание/проверка ZIP → обслуживание → проверенная
копия файлов и DDL/строк БД → миграции → переключение каталога версии → отдельные
HTTP health-check → завершение либо восстановление.

Появились `/owner/?section=updates`, `/admin/?section=updates` и независимый
`/updates/recovery.php`. Последний не использует активный выпуск и может
авторизовать начавшего обновление владельца даже при повреждённых таблицах входа.
Подробности, ограничения и восстановление: [UPDATES.md](UPDATES.md).

## Что проверено фактически

Изолированный стенд: PHP 8.2.12, Apache 2.4, MariaDB 10.4 на loopback 3319;
платформа на 8019, клиентская Content на 8029. Боевые записи не использовались.
Проверки выполняли настоящие HTTP-запросы, ZIP, RSA-подписи, DDL и восстановление.

- Успешная публикация/повтор публикации, проверка лицензии и каталога, установка,
  работа API и страницы после переключения, ручной возврат прежней версии.
- Успешные ALTER/UPDATE/CREATE TABLE с сохранением результата и последующим
  восстановлением исходной схемы и данных.
- Ошибка после уже выполненных DDL/DML → автоматический откат.
- Валидный PHP-пакет с ошибкой выполнения API новой версии → health-check
  обнаруживает сбой → прежний код и БД восстанавливаются.
- Потеря роли owner после миграции → health-check отменяет установку;
  независимый вход начавшего процесс владельца остаётся доступным до восстановления.
- HTML панели с отсутствующими JS-файлами → проверка ресурсов отклоняет выпуск
  и восстанавливает рабочее состояние. Для публичных ресурсов задаются 0755/0644.
- Реальное аварийное завершение CLI PHP кодом 77 после переименования `byp_users`:
  новое подключение через независимый экран, вход исходным паролем владельца,
  продолжение восстановления, возврат работоспособного API/сайта.
- Повреждение gzip-копии → отказ до удаления таблиц и сохранение обслуживания;
  восстановление исправного файла → повторное продолжение успешно.
- Сравнение схем и всех строк до/после отката, включая LONGTEXT длиннее 1 КиБ,
  бинарный BLOB, вычисляемый столбец и default timestamp.
- Приостановленная лицензия запрещает право нового обновления, но не мешает
  ручному откату. Конфигурация, загрузки и файлы проекта сохраняют SHA-256.
- Отказ нестандартному публичному PHP-входу в preflight без изменения БД и без
  оставленного maintenance.
- Во время обслуживания обычные запросы CMS получают 503; прямой `api/app.php`,
  PHP активного release, журналы и копии недоступны по HTTP. Проверены CSRF,
  анонимные запросы, повтор начального запроса, повтор завершённого шага/отката
  и запрет параллельного обновления.
- Начальные JS/CSS и public path ленивых Webpack-модулей используют один release.
  После отката отдельно проверены 13 реальных ресурсов восстановленной панели.
- Новый ZIP и ранее выданный архив содержат стабильный bootstrap. Приватные
  runtime-данные и ключ подписи в пакеты не включаются.

43 проверки подписи, приватного хранилища, файловых путей, manifest, SQL-границ, подменённого ZIP
и symlink; 57 регрессионных frontend/deployment/install-тестов; 49 проверок
лицензионной политики, 10 кэша лицензии, 27 массовых действий. Production export,
TypeScript, ESLint нового компонента и PHP lint.

Количество HTTP-шагов зависит от числа файлов в снимке и не является числом
независимых пользовательских сценариев. Тестовые ключи, дампы и fault-пакеты
находятся только в игнорируемом `outputs/acceptance/`. Боевого fault-API нет.

## Что не подтверждено

Визуальная и мобильная приёмка новых экранов пока не выполнена: после попыток
подключения инструмент всё ещё сообщает `Local browser use is disabled in Work
settings`. Наличие HTTP 200/проверка JS/CSS не заменяют реальную проверку интерфейса.

Обновление реальной внешней клиентской установки и публикация выпуска для всех
боевых клиентов не выполнялись. Платформа и demo получают код через штатный CI/FTP;
клиентский каталог публикует владелец. Фактический run и повторная проверка боевых
маршрутов указываются в отчёте после успешной выкладки.

Первый post-deploy smoke-check обнаружил HTTP 200 для подготовленного ZIP:
Nginx 1.20.2 отдавал ZIP в обход существующего запрета Apache. В unsigned candidate
нет конфигурации или ключа подписи. Одних `.htaccess` оказалось недостаточно:
журналы, копии и feed вынесены за DocumentRoot, candidate заменён PHP-контейнером
с HTTP 403/`__halt_compiler`, старый публичный ZIP исключён из выкладки.
HTTP 403 контейнера и недоступность старого ZIP остаются обязательными в CI.

Эта приёмка не объявляет готовность всей CMS к продаже. Остаются ранее обозначенные
реальная оплата/уведомления и соответствие тем заявленным возможностям. Процедура
работы с внешними cron, нестандартными схемами БД, большими данными и первоначальная
установка bootstrap на старые работающие сайты описаны как ограничения в UPDATES.md.
