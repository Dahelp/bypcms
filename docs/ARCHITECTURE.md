# BYPCMS 2 — архитектура платформы

## Главный принцип

Ядро, коммерческие модули и код конкретного проекта выпускаются независимо.
Клиентская доработка не меняет файлы ядра и не блокирует обновления.

```text
project/             индивидуальный дизайн и бизнес-правила
modules/             подключаемые возможности
contracts/           стабильные публичные интерфейсы
core/                авторизация, API, события, лицензия, обновления
```

## Границы слоёв

- `core` не импортирует код модулей и проекта;
- модуль зависит только от версионированных контрактов;
- модуль публикует manifest: идентификатор, версия, права, зависимости,
  миграции, пункты меню и обработчики событий;
- проект расширяет систему через те же контракты, что и официальный модуль;
- миграции каждого модуля имеют собственное пространство имён;
- удаление модуля не удаляет данные без отдельного подтверждённого шага.

## Контракт модуля

Каждый пакет обязан объявлять:

1. совместимый диапазон версий ядра;
2. необходимые возможности и разрешения;
3. зависимости от других модулей;
4. схемы настроек и миграции;
5. маршруты API и административные экраны;
6. события, которые он публикует и слушает;
7. health-check и сценарий безопасного отката.

Перед активацией система строит граф зависимостей, запускает проверки и
создаёт точку восстановления.

## Лицензирование

Лицензия подписывается сервером BYPCMS и привязана к:

- идентификатору установки;
- разрешённым доменам и окружениям;
- редакции продукта;
- списку коммерческих модулей;
- сроку обновлений и поддержки.

Установка хранит только публичный ключ проверки и подписанный entitlement.
Кратковременная недоступность лицензионного сервера не блокирует публичный
сайт: используется grace period. Истечение подписки отключает новые обновления
и поддержку, но не удаляет данные и не ломает уже работающий сайт.

## Обновления

1. Получить подписанный каталог версий.
2. Проверить версию PHP, базы данных и контракты модулей.
3. Создать резервную копию и maintenance token.
4. Развернуть новую версию рядом с активной.
5. Запустить миграции и health-check.
6. Атомарно переключить release.
7. При ошибке вернуть предыдущий release.

## Целевой backend

Для production CMS рекомендуется модульный монолит на PHP 8.3+ и PostgreSQL
или MySQL 8:

- Composer packages для ядра и модулей;
- PSR-11 container, PSR-14 events, PSR-15 middleware;
- REST/JSON API с OpenAPI;
- очередь для импорта, уведомлений и интеграций;
- object storage для медиа;
- отдельный license/update service;
- административный frontend как независимый клиент API.

Такой путь подходит обычному PHP-хостингу и оставляет возможность переноса в
контейнеры без смены прикладной архитектуры.
