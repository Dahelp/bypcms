# Боевая почта и фоновая обработка — 18 ноября 2026

## Причины и изменения

При начале проверки SMTP был включён и пароль сохранён, но отчёта фонового запуска не было. В панели GoHost существовало задание BYPCMS с расписанием `1 * * * *`: это один запуск в час на первой минуте. Для очереди требуется `* * * * *`.

Прежняя отметка `worker.json` не различала cron и кнопку Owner. Теперь CLI и ручные циклы имеют отдельные отчёты: время, случайный идентификатор запуска, длительность, результат и состояние completed/warning/failed. Старые отметки не подтверждают расписание; свежесть CLI проверяется за 15 минут, будущая дата отклоняется. Для приёмки расписания нужно увидеть несколько разных CLI-отчётов в соседние минуты. Ручной запуск их не переписывает.

Полный цикл защищён неблокирующей файловой блокировкой в приватном каталоге. Второй цикл пропускается без выполнения действий; после ошибки блокировка освобождается. Этапы сверки платежей, выдачи, срока счетов, возвратов и почты изолированы: исключение одного этапа отражается в отчёте и не мешает следующим. Деньги по банковскому счёту обработчик не подтверждает. Повторяется только выдача уже оплаченной покупки.

`commerce-worker.sh` выбирает поддерживаемый PHP CLI (включая alt-PHP GoHost), проверяет PHP >= 8.2 и расширения pdo_mysql/curl/openssl/mbstring/zip/zlib. Можно явно задать `BYPCMS_PHP_CLI` в окружении cron. Если подходящего CLI нет, обработка не начинается, диагностика выводится в stderr. Скрипт хранится с LF, запускается через `/bin/sh`, поэтому FTP не обязан сохранять executable bit. Команда в Owner формируется с настоящим абсолютным путём. Стандартный вывод успешных циклов подавляется в cron; ошибки остаются доступны штатному журналу/отчётам планировщика.

## Безопасный SMTP-тест

Owner → Настройки → Почта:

1. Сохранить транспорт и отправителя. Пустое поле пароля сохраняет прежний пароль.
2. Выбрать адрес владельца либо почтовый ящик SMTP. Если SMTP-логин не email, для второго варианта используется сохранённый отправитель. Произвольный адрес из запроса не принимается.
3. Поставить тестовое письмо в очередь: сервер возвращает его номер, повтор той же операции возвращает прежний номер. Изменение получателя с тем же токеном отклоняется.
4. «Отправить только тестовое письмо» обрабатывает только этот номер: не отправляет другие pending/retry, не меняет чужие зависшие lease и не запускает оплату, возврат или выдачу. Допускаются только сервисные smtp-test на сохранённый адрес. Повтор по принятому письму не отправляет его второй раз.
5. Открыть историю письма. «Принято SMTP» означает подтверждение сервера, а не получение во входящие. Проверить настоящий ящик и спам отдельно. При неизвестном результате сначала проверить получателя, затем явно разрешить повтор в почтовом центре.

Настройки SMTP остаются приватными и зашифрованными; пароль не выводится, не попадает в ZIP или Git. HTTP-запуск CLI остаётся закрытым. Нового публичного cron URL/токена нет.

Использован прежний отдельный loopback-стенд `outputs/purchase-acceptance-20261118`, MariaDB 3319, платформа 8019, TLS-приёмник 8465. Все заказы, банковские подтверждения, лицензии, домены и письма искусственные. Настоящие оплаты/возвраты не выполнялись.

- `tests/commerce-worker.test.php`: 14 проверок разделения CLI/manual, устаревшей/будущей даты, legacy-отметки, блокировки, прерывания и следующего успешного цикла; включено в CI.
- `tests/commerce-worker.integration.php`: 13 проверок настоящего CLI, восстановления выдачи после подтверждённой тестовой оплаты, отсутствия второй лицензии, изоляции сбоя срока счёта и повторной отправки после SMTP 451.
- `tests/worker-http.mjs`: 32 проверки авторизации/CSRF, выбранного письма, адресов теста, идемпотентности и неизменности CLI-отметки после ручного HTTP-цикла, включая два одновременных полных цикла.
- Повторены 67 SMTP lifecycle и 39 HTTP mail проверок, политики счетов/шаблонов, установка и маршруты Owner/Admin. Регрессия банковских счетов — 629 проверок на этом стенде.
- Переносимый shell-запуск выполнен с настоящим локальным PHP CLI; подготовка shell и синтаксис проверяются также в CI.

## Проверка после выкладки

До первого фонового запуска проверить реальные заказы и очередь. Исправить только задачу BYPCMS в хостинге: команда из Owner, все пять полей расписания `*`. Наблюдать разные CLI run_id и отметки времени минимум двух последовательных циклов. Убедиться, что ручной запуск не выдаётся за запуск расписания.

Отправить тест отдельно на ящик BYPCMS и адрес владельца; сверить историю SMTP с фактическим получением. Код/локальный приёмник не могут подтвердить получение реальным адресатом. Подробные результаты и скриншоты боевой проверки сохраняются в локальном игнорируемом каталоге, без паролей и платёжных данных. Существующий неизменяемый выпуск 2.7.1 повторно не публикуется.
