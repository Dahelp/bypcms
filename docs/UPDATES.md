# Обновление клиентской CMS и восстановление

## Сценарий владельца

1. В платформе открыть **Owner → Выпуски CMS** (`/owner/?section=updates`).
   После проверки подготовленной сборки подтвердить публикацию. Платформа
   подписывает manifest и каталог своим RSA-ключом. Публикация того же содержимого
   повторяется без создания второго выпуска; заменить код уже опубликованной
   версии нельзя — нужен новый номер.
2. В клиентской CMS открыть **Admin → Обновления** (`/admin/?section=updates`).
   Нажать «Проверить обновления». Проверяются лицензия, подпись каталога,
   исходная версия, редакция, модули и PHP.
3. Подтвердить «Создать копию и обновить». Пакет скачивается по проверенному HTTPS,
   сверяются размер, SHA-256, подпись и каждый файл. Новая версия распаковывается
   рядом с рабочей; PHP разбирается с `TOKEN_PARSE` до запуска.
4. После preflight включается обслуживание. Запросы рабочей CMS удерживают общий
   файловый lock; установщик получает исключительный. Новый запрос не сможет
   изменять БД во время копирования, миграций и восстановления.
5. Создаются и проверяются копии файлов и всех таблиц с DDL и данными.
   Только после завершения копии выполняются миграции. Версия переключается
   заменой одного JSON-указателя на том же файловом разделе.
6. Отдельными HTTP-запросами запускаются API новой версии, опубликованная страница
   (если есть) и Admin. После успешной проверки обслуживание снимается.

Конфигурация, ключ лицензии, пользовательские загрузки, `project/` и
`themes/custom/` не являются изменяемыми файлами выпуска. Бэкап содержит
конфигурацию, пользовательские файлы, текущий код и его ресурсы. Технические
рабочие каталоги обновления, прежние бэкапы и неактивные версии повторно
не копируются. Бэкапы остаются приватными в `_storage/updates/backups/<job>/`.
Они не отправляются на сервер BYPCMS.

## При сбое и прерывании

Каждый этап записывается в приватный журнал. Повтор начального запроса с тем же
идентификатором возвращает тот же процесс; повтор завершённого шага не устанавливает
пакет ещё раз. Закрытие вкладки останавливает только последующие шаги: текущий
PHP-запрос завершается с `ignore_user_abort`, а журнал позволяет продолжить.

- Ошибка до изменения БД оставляет рабочую версию и данные без изменений.
- Ошибка миграции или health-check переводит процесс в восстановление. Клиентский
  интерфейс продолжает шаги автоматически; если вкладка закрыта — их можно возобновить.
- При аварийном завершении PHP посреди миграции следующий шаг видит `inflight`
  и восстанавливает копию, не выполняя DDL второй раз.
- До удаления таблиц повторно проверяются SHA-256 копий. Повреждённая копия
  оставляет обслуживание включённым и показывает `recovery_required`.
- Восстановление возвращает DDL, строки и код из снимка в отдельный каталог версии.
  Если запрос оборвался во время восстановления таблицы, повтор заново создаёт
  именно эту таблицу; уже восстановленные таблицы не дублируются.
- Можно вручную откатить текущий установленный выпуск. Интерфейс предупреждает:
  изменения записей после создания копии будут потеряны. Пользовательские файлы
  не удаляются и не перезаписываются пакетами обновления/отката.
- Для отката не требуется действующая лицензия или связь с сервером лицензий.

**Независимое восстановление:** `/updates/recovery.php`. Эта страница и её API
не загружают код активного выпуска. На неё ведёт ссылка со страницы обслуживания.
Вход выполняется существующим паролем владельца. Если миграция повредила таблицы
авторизации, во время обслуживания можно войти как владелец, начавший процесс:
исходный hash его пароля сохранён зашифрованным в приватном журнале. Есть CSRF,
ограничение попыток по адресу и проверка owner. Пароль не меняется и не публикуется.

Сначала нажать «Продолжить процесс». При необходимости выбрать восстановление
копии. Если нет места, нет прав записи или повреждена копия, устранить причину
на хостинге и повторить продолжение. Нельзя вручную снимать maintenance с
непроверенной БД. При потере самого стабильного bootstrap/конфигурации требуется
восстановление этих файлов из хостинговой копии; этот механизм не заменяет
внешний бэкап от потери диска или всего аккаунта.

## Устройство и границы первой версии

Стабильные точки входа: `api/index.php`, `admin/index.php`, клиентский `index.php`,
`updates/`, `_core/Update*.php`. Они не заменяются пакетами. Прикладной API находится
в `api/app.php`; прямой HTTP-вызов этого файла запрещён. `_releases/` закрыт от HTTP.
Ресурсы Admin хранятся по адресу `/_update-assets/<release>/_next/`; меняются и HTML,
и public path Webpack, поэтому начальные и ленивые модули относятся к одной версии.

`_storage/updates/active.json` выбирает код; `jobs/` хранит ход процесса, `work/` —
проверяемый пакет и staging, `backups/` — проверенные снимки. Не передавайте
`_storage` в Git/ZIP клиента. Для внешней копии сохраняйте конфигурацию, БД,
пользовательские файлы и каталог обновлений с журналами и снимками.

Поддерживаются PHP 8.2+, Apache с `.htaccess`, PDO MySQL/MariaDB, OpenSSL, cURL,
ZipArchive и zlib. Файловые операции должны выполняться на одном разделе.
PHP нужны права записи в корень установки, `_storage`, `_releases` и `_update-assets`.
Права БД проверяются до миграций: SELECT, INSERT, UPDATE, DELETE, CREATE, DROP,
ALTER, INDEX, REFERENCES либо ALL PRIVILEGES непосредственно на БД/сервере.
Необычная схема прав через роли требует отдельной приёмки и останавливает preflight.

Первая версия предназначена для отдельной БД с таблицами InnoDB. Представления,
триггеры, хранимые программы, события БД и нестандартные публичные PHP-входы
требуют интеграции обслуживания/бэкапа; обнаружение останавливает процесс до
изменения данных. Внешние cron/CLI-писатели должны быть остановлены владельцем
на время операции: файловый lock координирует HTTP-запросы CMS, а не чужие процессы.

Консервативные пределы: пакет 50 МБ, распаковка 200 МБ, до 3000 файлов,
копируемые файлы сайта 512 МБ, оценка БД 256 МБ, одна строка дампа 32 МБ.
Проверяется свободное место с запасом. При превышении нужен внешний бэкап и
отдельная процедура; обновление не начинается. Автоматического удаления копий нет.
Выносите старые завершённые копии на внешнее хранение и освобождайте место
контролируемо; не удаляйте текущую версию или незавершённую операцию.

Для уже установленных пакетов, выпущенных до появления bootstrap обновлений,
нужно однократно развернуть новые управляемые файлы CMS из актуального пакета
с хостинговой резервной копией. Сохранить `_storage`, uploads, project и custom
шаблоны; не запускать повторную установку БД. После этого работает штатный механизм.
Старые ещё не установленные покупки при скачивании получают bootstrap и актуальный
открытый ключ. Это обновляет выдаваемый архив, а не изменяет чужую работающую установку.

Платформа BYPCMS и статическое demo публикуются прежним CI/FTP. Клиентский updater
не применяется к платформе и не меняет записи её клиентов. Выпуск клиентской CMS
публикует владелец после проверки подготовленной сборки.

## Выпуск и проверка

`pnpm build:ftp` также создаёт приватный `_private/update-candidate.zip`.
Сборка: `php scripts/build-update.php out <candidate.zip> [version]`.
Manifest перечисляет точные исходные версии, редакции, требуемые модули,
минимальный PHP, файлы с размерами/SHA-256 и именованные SQL-миграции.
Миграции допускают одиночные CREATE TABLE/ALTER TABLE/UPDATE/INSERT/DELETE
в пространстве `byp_`; произвольный SQL из HTTP не принимается.
Номер версии и миграции меняются разработчиком перед новым выпуском.

Проверки: `php tests/update-package.test.php`, `node tests/updates-http.mjs
<local-fixture.json>`, `node tests/update-faults-http.mjs <qa-directory>`.
Интеграционные тесты допускают только отдельный loopback-стенд с MySQL на 3319.
Fault injection находится в CLI-тесте; боевые маршруты не имеют тестовых команд
поломки, выключения проверок или пропуска резервной копии.

Основание для полного восстановления DDL, а не обещания SQL rollback:
[MySQL: implicit commits](https://dev.mysql.com/doc/refman/8.4/en/implicit-commit.html).
